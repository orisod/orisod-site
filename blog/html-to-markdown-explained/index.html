How HTML Actually Becomes Markdown

Copy a formatted paragraph from a webpage, paste it somewhere that only understands Markdown, and it just works — headings stay headings, bold stays bold, links stay links. That conversion looks instant, but it's really a small, structured translation process running underneath, one HTML element at a time.

A tree walk, not a text transformation

The browser doesn't hand a converter raw HTML text to pattern-match against — it hands over the DOM, the parsed tree structure the browser already built to render the page: this paragraph contains this bold span, which contains this text node, and so on. A converter walks that tree from the top down, and for every node it encounters, asks one question: what Markdown syntax represents this specific element? A `` becomes text wrapped in `**`, an `

` becomes a line starting with `##`, an `` becomes `[text](url)`. The output is built by recursively converting each node's children first, then wrapping the result in whatever syntax that node's tag calls for.

Why this is a mapping, not a translation

Every HTML element needs an explicit rule saying what Markdown it becomes — there's no automatic or general-purpose way to derive one from the other, because Markdown wasn't designed to represent everything HTML can. A `

` with a custom CSS class carries no Markdown equivalent at all; a converter simply treats it as an invisible wrapper and keeps its content. This is why a mature converter ships with dozens of built-in rules (one per common tag) and lets you register more for anything unusual it encounters.

Why a table needs a heading row to convert at all

Markdown's table syntax has a hard requirement HTML tables don't: a separator line of dashes directly under the header row, which is what tells a Markdown renderer where the header ends and the body begins. An HTML table with no `` header cells has no natural source for that line, so a converter genuinely cannot produce a valid Markdown table from it — the honest options are to skip the conversion and leave the original table as raw HTML embedded in the output, or to treat the first row as a header by assumption. This isn't a limitation of the converter; it's a structural requirement of the Markdown table format itself.

What never survives the trip

Markdown was deliberately kept small: it standardizes headings, emphasis, links, lists, quotes, code, and (in extended dialects) tables — and nothing else. Font choices, custom colors, precise spacing, multi-column layouts, and embedded scripts or styles have no Markdown representation, so a converter drops them rather than inventing non-standard syntax to approximate them. This is a feature, not a gap: Markdown's whole value proposition is being readable as plain text and portable across tools, which only holds if everyone agrees on the same small vocabulary.

Quick answers

Why does pasted content sometimes carry unexpected formatting? Rich-text paste from apps like Word or Google Docs often wraps content in extra styling elements the app added for its own rendering — a converter still extracts the underlying structure correctly, but very unusual source formatting can occasionally produce noisier output than clean HTML would.

Can a link with no visible text convert properly? Yes — the link's own text content becomes the bracketed label and its href becomes the URL, exactly as with any other link, regardless of how that text was styled.

Is HTML-to-Markdown conversion reversible? Not perfectly — converting Markdown back to HTML recovers the structure, but anything Markdown couldn't represent in the first place (custom styling, layout) is already gone and can't be reconstructed from the Markdown alone.
