What a Checksum Actually Proves (and What It Doesn't)

A software vendor publishes a line like a3f5...9c2 next to a download link, and somehow that's supposed to reassure you the file is fine. It's a reasonable thing to trust without knowing why — but the "why" turns out to be a genuinely useful piece of computer science, with a real boundary on what it can and can't tell you.

A hash function's one job

A hash function takes an input of any size — a word, a sentence, a multi-gigabyte file — and produces a fixed-length string of characters, deterministically: the same input always produces the exact same output, every time, on any computer. Feed it a different input, even one bit different, and the output looks completely unrelated to the previous one. That's the entire mechanism. A "checksum" is just that output, used specifically to check that something matches.

Why one flipped bit changes everything

This is the property that makes a checksum useful at all: a well-designed hash function is built so that changing even a single bit of the input scrambles roughly half of the output bits, unpredictably. There's no "mostly the same" hash for "mostly the same" file — a one-byte difference and a completely rewritten file both produce outputs that look equally unrelated to the original. This is called the avalanche effect, and it's precisely why a matching hash is meaningful: there's essentially no way for corrupted or altered data to accidentally produce the same hash as the original.

Integrity is not authenticity

Here's the boundary that matters most: a matching checksum proves the file you have is byte-for-byte identical to the file the checksum was computed from. It proves nothing about who computed that checksum or where the file actually came from. If both the file and its published checksum are hosted on a compromised server, an attacker can replace both together, and everything will still "match." A checksum answers "was this corrupted in transit?", not "can I trust the source?" — for the second question, you need something like a cryptographic signature, which relies on a private key an attacker doesn't have, not just a hash anyone can recompute.

Why "broken" algorithms are still around

MD5 and SHA-1 are considered cryptographically broken because researchers found practical ways to construct two different inputs that hash to the same output — a "collision" — through deliberate, expensive effort. That matters enormously for security-critical uses like digital signatures, where an adversary might want to swap in a malicious document that hashes the same as a legitimate one. It matters far less for catching accidental corruption — a truncated download, a bad disk sector, a network glitch — because those failures aren't an adversary engineering a specific collision, they're essentially random damage, and even a "broken" hash function still fails an avalanche test against random damage. That's the real reason file-integrity checksums still commonly use MD5 or SHA-1: the threat model is corruption, not an adversary.

Quick answers

If two files have the same hash, are they definitely identical? For any hash function without a known practical collision method (SHA-256 and above, currently), yes for all realistic purposes — the odds of two different files matching by chance are astronomically small.

Why do checksums look like random letters and numbers? They're just a byte sequence (the raw output of the hash function) displayed in hexadecimal, since raw bytes aren't easy to read or copy-paste reliably as text.

Does a longer hash mean a more secure algorithm? Generally yes within the same algorithm family — SHA-512 has more output bits than SHA-256, making brute-force and collision attacks harder — but algorithm design matters more than length alone, which is why MD5's 128-bit output is weaker than SHA-1's 160-bit output by more than the length difference alone would suggest.
