Text Case Styles Explained: When to Use camelCase, snake_case, and More

Every programming ecosystem has a house style for naming things, and it's rarely arbitrary — it usually comes down to what the language's own conventions expect, and what a case-insensitive filesystem or URL can and can't handle safely.

The naming styles, and what each one is actually for

Five styles cover almost every case you'll run into:

  • camelCase — first word lowercase, every following word capitalized, no separators (firstName). The default for variables and function names in JavaScript, Java, and most C-family languages.
  • PascalCase — same as camelCase but the first word is also capitalized (FirstName). Used for class and type names in the same languages, precisely to distinguish a type from a variable at a glance.
  • snake_case — all lowercase, words separated by underscores (first_name). The standard for variables and functions in Python and Ruby, and for database column names almost everywhere.
  • kebab-case — all lowercase, words separated by hyphens (first-name). Used for URL slugs and CSS class names — hyphens are the one separator that's always safe in a URL without encoding.
  • CONSTANT_CASE (also called SCREAMING_SNAKE_CASE) — all uppercase, words separated by underscores (FIRST_NAME). Reserved specifically for constants, so an all-caps identifier signals "this value never changes" at a glance.

Why the convention matters more than the choice

None of these styles is technically superior — a JavaScript variable named first_name instead of firstName still works exactly the same. What breaks is consistency: mixing styles within one codebase forces every reader to context-switch for no reason, and some tools genuinely can't cross styles safely (a CSS class must be kebab-case-safe, a URL slug can't contain characters that need encoding, and a case-sensitive filesystem will treat MyFile and myfile as two different files while a case-insensitive one won't). The style itself is a convention; picking one and applying it consistently is what actually matters.

Where each style tends to show up

  • Variables and functions: camelCase (JavaScript, Java) or snake_case (Python, Ruby) — pick whichever your language's own standard library and style guide already use, not a personal preference.
  • Classes and types: PascalCase, almost universally, across the languages that distinguish them from variables at all.
  • URLs and file slugs: kebab-case — search engines and browsers treat hyphens as word separators in a URL, which underscores and camelCase don't get for free.
  • CSS classes: kebab-case is the long-standing convention (.nav-link), though some component-based frameworks use camelCase for CSS-in-JS.
  • Constants and environment variables: CONSTANT_CASE — the all-caps convention originated with C preprocessor macros and is still the standard for env vars and true constants today.

Quick answers

Is there a "correct" case for JSON keys? No hard rule, but camelCase is the de facto convention in JavaScript-heavy APIs, while snake_case shows up often in APIs written by Python/Ruby-first teams — match whatever the rest of that API already uses.

What's the difference between kebab-case and "dash-case" or "spinal-case"? Nothing — they're the same style under different names, all referring to lowercase words joined by hyphens.

Why do some style guides avoid underscores in URLs? Older search engines didn't reliably treat an underscore as a word separator (some still read first_name as one word, "first_name," rather than two), while a hyphen reliably splits into separate words — kebab-case avoids the ambiguity entirely.
