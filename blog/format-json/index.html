How to Format and Validate JSON (and the Syntax Rules That Actually Matter)

JSON looks close enough to a JavaScript object literal that it's easy to assume they're interchangeable — paste one where the other is expected, and a strict JSON parser will reject it. Here's exactly what JSON requires that plain JavaScript doesn't.

Where JSON is stricter than a JS object literal

JSON was deliberately designed as a small, unambiguous subset of JavaScript's object literal syntax — which makes the differences easy to overlook until JSON.parse() throws on something that looks perfectly reasonable. The four rules that trip people up most often: every key must be a double-quoted string (not unquoted, not single-quoted), every string value must also use double quotes, there can be no trailing comma after the last item in an object or array, and comments aren't allowed anywhere, even though they're valid JavaScript.

Why pretty-printing matters

An API response or a minified config file is usually returned as a single unbroken line — technically valid, but unreadable the moment you need to check a nested value or compare it against something else. Pretty-printing (adding consistent indentation and line breaks) doesn't change the data at all, it just re-serializes the same parsed structure with whitespace a human can actually scan.

When to minify instead

Minifying does the opposite: it strips every non-essential space, so the same data takes less room. That matters when you're pasting JSON somewhere with a character limit, storing it compactly, or sending it over a network where every byte counts — none of which benefit from indentation that a machine doesn't need.

Common JSON syntax errors and what causes them

  • Trailing comma — leaving a comma after the last property or array item, a habit carried over from JavaScript (where it's harmless) or from editing a list and forgetting to remove the old separator.
  • Single-quoted strings — copying a JavaScript object literal directly, where single and double quotes are interchangeable; JSON only accepts double quotes.
  • Unquoted keys — same source: JavaScript allows bare identifier keys like name:, JSON requires "name":.
  • Mismatched or missing brackets — an extra or missing {, }, [, or ], usually from manually editing nested data by hand.
  • A missing comma between properties — easy to miss when reformatting JSON by hand instead of letting a formatter do it.

Quick answers

Can JSON have comments? No — not //, not /* */. If you need annotated config, JSON isn't the right format (JSON5 and JSONC are separate, non-standard extensions that add comment support, but a strict JSON parser rejects both).

Does key order matter in JSON? Not to the data itself — two objects with the same keys in a different order represent the same value. It only matters if you're comparing raw text (like diffing two files), which is exactly what sorting keys before comparing is for.

Why does my JSON.parse error just say "position 45" instead of a line number? That's how V8 (Chrome's JavaScript engine) reports it — a formatter can convert that character offset into a line and column by counting newlines up to that position, which is exactly what a helpful error message should show instead.
