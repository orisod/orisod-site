How to Recombine Front and Back Duplex Scans Into One PDF

A scanner that can't scan both sides of a page automatically forces a workaround that's older than the scanner itself: scan every front side in one pass, flip the whole stack over, scan every back side in a second pass, and end up with two separate files that need to become one correctly ordered document.

Why this produces two files instead of one

A duplex-capable scanner flips each page internally as it feeds, so a single pass captures front and back and interleaves them automatically. A simplex-only (single-sided) scanner or feeder has no way to do that — the only way to capture both sides of a stack is two separate passes, and each pass naturally produces its own file. Nothing about the content is wrong at this point; the two files just haven't been woven together yet.

Why the second file is so often backwards

Here's the part that trips people up: after scanning all the front sides, the stack comes out of the feeder in reverse order relative to how it started (page 1 ends up on the bottom of the output stack, since each sheet exits on top of the last). To scan the back sides without manually re-sorting the whole stack, the natural move is to flip the entire stack over as one block and feed it straight back in — but flipping a stack over reverses which page is now first. The back-side scan ends up capturing the last page's back side first and the first page's back side last: the exact reverse of the front-side file's order.

Interleaving: putting the two files back together

Once both files exist, recombining them is a matter of alternating pages from each: front 1, back 1, front 2, back 2, and so on, so the final document reads the way the physical stack originally did. If the back-side file is in reverse order (the common case above), it has to be read from its last page backward during that interleave — matching back-side page 1 (which is actually stored last in the file) with front-side page 1, and so on — rather than pairing pages by their raw position in each file.

Why this stays vector instead of becoming an image

Interleaving doesn't need to inspect or modify what's drawn on a page — it only needs to copy whole pages and place them in a new order. A PDF library can copy a page's content directly, exactly as Merge PDF already does when combining whole files, without ever rendering it to pixels. That's different from operations like a color filter, which has no choice but to rasterize because it needs to touch individual pixel values — interleaving never needs that, so there's no reason to pay the cost of it.

Quick answers

What if the front and back files have different page counts? That usually means a sheet was skipped or double-fed during one of the two passes — worth checking against the original document, but a well-behaved interleaving tool should still handle it by pairing what it can and appending the rest, rather than failing outright.

Will the back sides be right-side up? Interleaving only reorders pages — if a back-side scan came out rotated 180° (common with certain sheet-flip mechanics), that's a separate rotation step, not something reordering pages fixes on its own.

Does the front-side file ever need reversing too? Not in the standard workflow described here — only the pass that involved physically flipping the stack ends up reversed; the first pass keeps the stack's natural order.
