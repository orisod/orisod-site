Why a PDF Color Filter Rasterizes Every Page (and What That Costs You)

A color filter on a photo just changes pixels that were already there. A color filter on a PDF is a different job entirely — most PDF pages don't have "pixels" to recolor in the first place, so the tool has to manufacture some before it can do anything.

Why a PDF page usually isn't made of pixels

Text and shapes in a typical PDF are stored as vector instructions — draw this letterform at this size at this position, stroke this line, fill this shape — resolution-independent descriptions that a PDF viewer turns into pixels only at the moment it displays or prints the page. There's no fixed grid of colored dots to loop over and recolor, the way there is in a JPEG or PNG. A color filter, by definition, needs to touch individual pixels — grayscale needs a pixel's red/green/blue values to compute one gray value, sepia needs those same values to compute a tinted replacement — so it needs pixels to exist first.

What rasterizing actually means here

The fix is to render each page the same way a PDF viewer would to display it on screen, except capturing the result as a bitmap instead of showing it — effectively taking a very precise screenshot of each page. That screenshot is genuinely made of pixels, so the filter's per-pixel math can run on it normally. The filtered bitmap then gets placed into a brand-new PDF, one image per page, sized to match the original page dimensions.

The real cost: text stops being text

Once a page is a pixel image, whatever text was on it is now just colored dots that happen to look like letters — the same situation a scanned document is already in. Selecting a sentence, searching for a word, or copying a paragraph all stop working, because there's no longer any actual text there to select, search, or copy — only its picture. This isn't a bug or a missing feature; it's an unavoidable consequence of doing pixel-level color work on content that didn't start out as pixels. The fix, if searchable text matters afterward, is the same one that fixes any scanned document: running the result through OCR to add a text layer back.

Choosing a resolution: the quality tradeoff

Because the output is now an image, its sharpness depends entirely on how many pixels it was rendered at — this is where a genuine tradeoff shows up. Render too small and text edges look chunky or blurry when the page is viewed at full size or printed; render very large and the resulting PDF balloons in file size for very little visible benefit past a certain point. Rendering at roughly twice the page's normal display resolution before filtering is a practical middle ground: sharp enough that filtered text stays legible at normal reading and printing sizes, without inflating the file the way an even higher resolution would.

Quick answers

Does this change the PDF's page size or layout? No — each new page is sized to match the original page's dimensions; only the content becomes a single image instead of live vector elements.

Why JPEG instead of PNG for the filtered pages? JPEG's lossy compression keeps file size far smaller for photographic-style content at a quality level where the difference is not visually obvious, which matters more here since every single page is now a full-page image instead of light text instructions.

Is there any way to filter a PDF without losing selectable text? Not for a true pixel-level color effect — anything that only needs to recolor specific known elements (like a solid background color) could theoretically be done without rasterizing, but a general filter that inspects and changes arbitrary pixel colors fundamentally needs pixels to work with.
