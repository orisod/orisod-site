Cómo formatear y validar JSON (y las reglas de sintaxis que realmente importan)

JSON se parece tanto a un objeto literal de JavaScript que es fácil asumir que son intercambiables — pega uno donde se espera el otro, y un analizador JSON estricto lo rechazará. Esto es exactamente lo que JSON exige y JavaScript no.

Dónde JSON es más estricto que un objeto literal de JS

JSON fue diseñado deliberadamente como un subconjunto pequeño e inequívoco de la sintaxis de objetos literales de JavaScript — lo que hace que las diferencias sean fáciles de pasar por alto hasta que JSON.parse() falla con algo que parecía perfectamente razonable. Las cuatro reglas que más confunden: cada clave debe ser una cadena entre comillas dobles (no sin comillas, no con comillas simples), cada valor de tipo cadena también debe usar comillas dobles, no puede haber una coma sobrante después del último elemento de un objeto o array, y los comentarios no están permitidos en ningún lugar, aunque sean válidos en JavaScript.

Por qué importa la sangría (pretty-printing)

Una respuesta de API o un archivo de configuración minificado suele venir como una sola línea sin cortes — técnicamente válido, pero ilegible en el momento en que necesitas revisar un valor anidado o compararlo con otra cosa. Aplicar sangría no cambia los datos en absoluto, simplemente vuelve a serializar la misma estructura ya analizada con espacios en blanco que una persona puede leer.

Cuándo minificar en su lugar

Minificar hace lo contrario: elimina todo espacio no esencial, así que los mismos datos ocupan menos espacio. Eso importa cuando vas a pegar el JSON en algún sitio con límite de caracteres, guardarlo de forma compacta, o enviarlo por una red donde cada byte cuenta — ninguno de esos casos se beneficia de una sangría que una máquina no necesita.

Errores de sintaxis JSON comunes y sus causas

  • Coma sobrante — dejar una coma después de la última propiedad o elemento de un array, un hábito heredado de JavaScript (donde es inofensivo) o de editar una lista y olvidar quitar el separador anterior.
  • Cadenas con comillas simples — copiar directamente un objeto literal de JavaScript, donde comillas simples y dobles son intercambiables; JSON solo acepta comillas dobles.
  • Claves sin comillas — misma causa: JavaScript permite claves como identificadores sin comillas (nombre:), JSON exige "nombre":.
  • Corchetes o llaves que no coinciden o faltan — un {, }, [ o ] de más o de menos, normalmente por editar datos anidados a mano.
  • Falta una coma entre propiedades — fácil de pasar por alto al reformatear JSON a mano en lugar de dejar que lo haga un formateador.

Respuestas rápidas

¿Puede el JSON tener comentarios? No — ni // ni /* */. Si necesitas configuración con anotaciones, JSON no es el formato adecuado (JSON5 y JSONC son extensiones separadas y no estándar que añaden soporte de comentarios, pero un analizador JSON estricto rechaza ambas).

¿Importa el orden de las claves en JSON? No para los datos en sí — dos objetos con las mismas claves en distinto orden representan el mismo valor. Solo importa si estás comparando el texto sin procesar (como al comparar dos archivos), que es exactamente para lo que sirve ordenar las claves antes de comparar.

¿Por qué mi error de JSON.parse solo dice "position 45" en lugar de un número de línea? Así lo reporta V8 (el motor de JavaScript de Chrome) — un formateador puede convertir ese desplazamiento de caracteres en una línea y columna contando los saltos de línea hasta esa posición, que es exactamente lo que debería mostrar un mensaje de error útil.
