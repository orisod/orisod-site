Estilos de mayúsculas y minúsculas explicados: cuándo usar camelCase, snake_case y más

Cada ecosistema de programación tiene un estilo propio para nombrar cosas, y rara vez es arbitrario — normalmente depende de lo que espera la convención del propio lenguaje, y de lo que un sistema de archivos que no distingue mayúsculas o una URL pueden manejar sin problemas.

Los estilos de nomenclatura, y para qué sirve cada uno

Cinco estilos cubren casi todos los casos que te vas a encontrar:

  • camelCase — primera palabra en minúscula, cada palabra siguiente capitalizada, sin separadores (firstName). El estilo por defecto para variables y nombres de funciones en JavaScript, Java y la mayoría de los lenguajes de la familia C.
  • PascalCase — igual que camelCase pero la primera palabra también va capitalizada (FirstName). Se usa para nombres de clases y tipos en esos mismos lenguajes, precisamente para distinguir un tipo de una variable de un vistazo.
  • snake_case — todo en minúsculas, palabras separadas por guiones bajos (first_name). El estándar para variables y funciones en Python y Ruby, y para nombres de columnas de bases de datos casi en todas partes.
  • kebab-case — todo en minúsculas, palabras separadas por guiones (first-name). Se usa para slugs de URL y nombres de clases CSS — el guion es el único separador que siempre es seguro en una URL sin necesidad de codificación.
  • CONSTANT_CASE (también llamado SCREAMING_SNAKE_CASE) — todo en mayúsculas, palabras separadas por guiones bajos (FIRST_NAME). Reservado específicamente para constantes, así que un identificador en mayúsculas señala de un vistazo "este valor nunca cambia".

Por qué importa más la convención que la elección

Ninguno de estos estilos es técnicamente superior — una variable de JavaScript llamada first_name en lugar de firstName funciona exactamente igual. Lo que se rompe es la consistencia: mezclar estilos dentro de un mismo código obliga a cada persona que lo lee a cambiar de contexto sin necesidad, y algunas herramientas realmente no pueden mezclar estilos sin problemas (una clase CSS debe ser compatible con kebab-case, un slug de URL no puede contener caracteres que necesiten codificación, y un sistema de archivos sensible a mayúsculas tratará MiArchivo y miarchivo como dos archivos distintos mientras que uno insensible no lo hará). El estilo en sí es una convención; elegir uno y aplicarlo con consistencia es lo que realmente importa.

Dónde suele aparecer cada estilo

  • Variables y funciones: camelCase (JavaScript, Java) o snake_case (Python, Ruby) — usa el que ya use la biblioteca estándar y la guía de estilo de tu lenguaje, no una preferencia personal.
  • Clases y tipos: PascalCase, casi universalmente, en los lenguajes que los distinguen de las variables.
  • URLs y slugs de archivos: kebab-case — los motores de búsqueda y los navegadores tratan los guiones como separadores de palabras en una URL, algo que los guiones bajos y el camelCase no obtienen de forma gratuita.
  • Clases CSS: kebab-case es la convención de siempre (.nav-link), aunque algunos frameworks basados en componentes usan camelCase para CSS-in-JS.
  • Constantes y variables de entorno: CONSTANT_CASE — la convención de mayúsculas totales se originó con las macros del preprocesador de C y sigue siendo el estándar para variables de entorno y constantes reales hoy en día.

Respuestas rápidas

¿Hay un estilo "correcto" para las claves de un JSON? No hay una regla estricta, pero camelCase es la convención de facto en APIs con mucho JavaScript, mientras que snake_case aparece a menudo en APIs escritas por equipos que priorizan Python o Ruby — usa el que ya utilice el resto de esa API.

¿Cuál es la diferencia entre kebab-case y "dash-case" o "spinal-case"? Ninguna — son el mismo estilo con distintos nombres, todos se refieren a palabras en minúscula unidas por guiones.

¿Por qué algunas guías de estilo evitan los guiones bajos en las URLs? Los motores de búsqueda más antiguos no siempre trataban un guion bajo como separador de palabras (algunos todavía leen first_name como una sola palabra, "first_name", en lugar de dos), mientras que un guion siempre divide en palabras separadas — kebab-case evita esa ambigüedad por completo.
