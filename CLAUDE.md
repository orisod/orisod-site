# Orisod — Project Context for Claude Code

## Permanent rules

**Always run `git pull` at the start of every session before making changes**, since manual edits sometimes happen directly on GitHub's web editor.

**Never commit or push directly to `main`.** Every change, without exception, goes through: create a feature branch → commit → push the branch → open a PR → wait for CI to pass → merge only after the user explicitly approves the merge. This applies regardless of how the request is phrased (e.g. "commit this," "push it") — those instructions mean "do it via the branch/PR flow," not "commit straight to main." If a step in this flow seems to conflict with a direct instruction, stop and confirm with the user rather than defaulting to the direct-to-main path.

## What this project is

Orisod (orisod.com) is a free, browser-based toolkit for images and PDFs — think a lighter, privacy-first alternative to iLovePDF/TinyWow. Static HTML site, deployed via GitHub Pages, folder-based routing (`/tool-name/index.html`).

**Core brand promise:** everything runs 100% client-side in the browser. Files are never uploaded to any server. This is the main differentiator and is mentioned explicitly on the home page and in every tool's FAQ section.

**Contact:** orisod.lab@gmail.com (JS-obfuscated on the site to avoid scraper bots — never hardcode it as plain `mailto:` text in HTML)

## Tech stack

- Plain HTML/CSS/JS, no build step, no framework
- GoatCounter analytics on every page (replaced Google Analytics 4 on 2026-10-26): one snippet in `<head>`, with `count.js` self-hosted and patched so URL parameters stay in the browser. See **Analytics (GoatCounter)** below.

## Analytics (GoatCounter)

Since 2026-10-26 the site counts visits with hosted GoatCounter (site code `orisod`, dashboard https://orisod.goatcounter.com). It uses no cookies, stores no visitor IDs in the browser and keeps only aggregate counts. It holds the IP address and User-Agent in memory for up to 8 hours to tell visits apart, and runs on Hetzner servers in Germany and Finland. Individual pageviews stay **off**, the **Size** and **Language** collection settings are **off**, and data retention is set to **365 days**. The privacy policy relies on all of these settings (it lists only page views, referring websites, approximate country, browser type and operating system, and says language and screen size aren't kept), so don't change any of them in the dashboard without updating `/privacy/` and `/es/privacy/`. Never call it "anonymous" and never claim IPs aren't processed. Google Analytics is gone for good: the GA4 property still exists but nothing on the site sends to it.

- **The snippet** is the same on every production page (all `index.html` pages plus `404.html`, EN and ES), in `<head>` right after the theme script, where the GA4 tag used to be:
  ```html
  <!-- GoatCounter: cookie-free visit counts (see /privacy/). count.js is a pinned, self-hosted copy; visits are sent to orisod.goatcounter.com -->
  <script data-goatcounter="https://orisod.goatcounter.com/count" async src="/assets/goatcounter/count.js"></script>
  ```
  No settings attribute, no events, no other library. Copy it from any existing page when adding one.
- **`count.js` is a pinned local copy with an Orisod privacy patch**, self-hosted at `assets/goatcounter/count.js`, so pages don't download a script from GoatCounter. Every visit is still sent to the endpoint above, and the privacy policy says so.
  - **Upstream:** the file served at `https://gc.zgo.at/count.js` on 2026-10-26, identical to `public/count.js` in [arp242/goatcounter](https://github.com/arp242/goatcounter) at commit `478f026eb9` (2026-04-07; newer than the v2.7.0 tag, and `gc.zgo.at/count.v5.js` is an older script). Upstream sha256 `792b7abd26c1fb6ae62906833e09a301251e2641816e69e4f95aba518f3fe3f0`, 9,213 bytes.
  - **The patch** (added 2026-10-27, exact diff in `scripts/goatcounter-privacy.patch`): upstream sends `location.search` as is in its `q` field, and also puts the query string into the page path (on pages without a canonical, like the 404) and the referrer (a same-site referrer is the full previous URL). None of its settings can turn that off. The patch rebuilds `q` from an allowlist of the parameters GoatCounter reads as a campaign or source (`utm_campaign`, `campaign`, `utm_source`, `ref`, `src`, `source`) and sends the path and referrer without their query string. Everything else, like the site search's `?search=` words, never leaves the browser. Every changed line is marked "Orisod privacy patch". Patched sha256 `2dbc3b65c7cb08f562a8cf87e17f99cf6a640b2760fb919b43eb34844120ab32`, 10,693 bytes. `.gitattributes` keeps `count.js` and the patch byte-for-byte (no CRLF conversion on Windows), or the checksum and the patch wouldn't match.
  - **License:** ISC (GoatCounter's `LICENSE` carves `public/count.js` out of the project's EUPL), which allows changes as long as the notice stays. The copyright line and ISC text required in every copy are in `assets/goatcounter/LICENSE.txt`, with a note about the patch. It sets no cookies. Its only `localStorage` use is the owner's `skipgc` flag, written only when a URL ends in `#toggle-goatcounter` (open any page with that ending to stop counting your own visits in that browser; open it again to undo). It doesn't count on localhost, private network addresses or `file:` pages, so a local test never sends a request: the real check is loading a page on orisod.com and seeing it in the dashboard.
- **Updating `count.js`** (no automatic updates):
  1. Download `https://gc.zgo.at/count.js` to a temporary folder (not into the repo). Diff it against the old upstream (`git apply -R` the patch on a copy of the current file gives it back) and read every change: new data sent, storage, network calls, anything built from the URL.
  2. Re-apply the patch to the new file: put it at `assets/goatcounter/count.js` and run `git -c core.autocrlf=false apply scripts/goatcounter-privacy.patch`. If it doesn't apply cleanly, redo the same changes by hand and regenerate the patch with `diff -u` (header lines `--- a/assets/goatcounter/count.js` / `+++ b/assets/goatcounter/count.js`, no timestamps). Check that nothing new in upstream reads `location` or `document.referrer` around the patch.
  3. Run `node scripts/test_goatcounter_privacy.js --upstream <the downloaded file>`. It must end with "All GoatCounter privacy checks passed": it proves that search words and unknown parameters aren't sent, campaigns still are, upstream does leak (so the test still sees leaks), and every visible result is the same with both files.
  4. Update the commit, date and both checksums here and in `LICENSE.txt`, and `COUNT_JS_SHA256`/`UPSTREAM_SHA256` (and `PATCH_MARKERS` if a patched line changed) in `scripts/check_analytics.py`. Then re-read the privacy policy against what the new version sends.
- **What it sends** (checked in the browser on 2026-10-27 with the test above): `p` the page path (from the canonical URL when there is one, without any query string), `r` the referrer without its query string (empty when there's none), `t` the page title, `s` the screen width, `b` a bot flag, `q` only the allowed campaign parameters (usually empty, so not sent), and `rnd` a random cache-buster. The browser itself adds the IP address, User-Agent and Accept-Language. Page titles never change at runtime except the 404 page's own translation, and no tool puts the user's data in the URL; keep it that way. The site search still uses `/tools/?search=<words>` (and the homepage's `?q=`), which the patch keeps out of the count.
- **`scripts/test_goatcounter_privacy.js`** (local only, not in CI) is the way to re-check all of this after any change to `count.js` or to how pages use the URL. It loads the pages in headless Chromium as `https://orisod.com/...` but answers every request from the local files and captures the counting request, so count.js behaves as in production (no `allow_local` needed) and nothing leaves the computer. It prints every field sent for a homepage, a tool page and a blog post, then runs the search, campaign, referrer and 404 scenarios.
- **`scripts/check_analytics.py`** (CI: `check-analytics`, also run by `verify_new_content.py`) fails on:
  - any page without exactly one copy of that snippet in `<head>`
  - any Google Analytics trace (gtag, googletagmanager, `dataLayer`, a G-/UA- ID, even the words "Google Analytics")
  - any other analytics or tracking service, or a `gc.zgo.at` script
  - a `count.js` that isn't the reviewed, patched copy, including an unpatched upstream copy, a missing patch line or upstream's `q: location.search` coming back

## Self-hosted libraries (`assets/vendor`) (started 2026-10-28, complete 2026-10-29)

**The self-hosting series is complete (2026-10-29):** no page needs an outside script host any more. A check of all 314 production pages and a headless load of 56 of them (every tool family, EN and ES) found no outside host contacted except orisod.goatcounter.com. The tools' third-party libraries moved off the CDNs one PR per group of libraries. The order was: small utilities first (spark-md5, qrcodejs, suncalc, turndown, turndown-plugin-gfm, done 2026-10-28), then pdf-lib (done 2026-10-28), PDF.js (with its worker, done 2026-10-28), the jsPDF family (jsPDF, jspdf-autotable, html2canvas, JSZip, done 2026-10-28), the Office libraries (docx, mammoth, SheetJS, done 2026-10-28), heic2any (unmodified, with the libheif/libde265 LGPL texts and a link to their source, done 2026-10-28), Tesseract (worker, the 3 LSTM `.wasm.js` core variants and the eng/spa language data, done 2026-10-28), and finally the privacy pages, the OCR FAQ and the open-source notice (PR 8, 2026-10-29; the strict guard itself landed with Tesseract). Since PR 8, `/privacy/` says the libraries and OCR PDF's engine and language data are served from orisod.com, OCR PDF's FAQ says its language data comes from orisod.com, and About (EN+ES, under "Your files stay on your device") has an open-source paragraph linking heic2any's `NOTICE.txt`, the libheif and libde265 source archives and the manifest. Library versions stayed as they were during the move; upgrades are separate PRs (the first: jsPDF 2.5.1 to 4.2.1 with autotable 3.8.4 to 5.0.9, 2026-11-01).

- **Layout:** `assets/vendor/<name>/<version>/<file>` plus that library's `LICENSE` in the same folder (and any extra notice files its license requires). Every file is **byte-identical** to its source URL: never minify, patch or re-save one. The one exception is a notice Orisod writes about a library (heic2any's `NOTICE.txt`, naming the LGPL code it bundles, and Tesseract's, listing its engine's libraries and the language data's origin): plain text, never code, marked `"written_by": "Orisod"` in the manifest instead of a `source`. `.gitattributes` has `assets/vendor/** -text` so line endings can't change a byte on Windows.
- **Manifest:** `assets/vendor/manifest.json` lists every library: `name`, `version`, SPDX `license` (plus a `license_note` when a choice was made, e.g. spark-md5's MIT option), `used_by` (the tool folders that load it), and for every file, for the `license_file` and for any `notice_files` (the license files of code a library bundles, like the four in JSZip's folder) its `path`, `source` URL, `sha256` and `bytes`. A notice file Orisod wrote has `"written_by": "Orisod"` in place of `source`; `check_vendor.py` allows that only for a `notice_files` entry that isn't a script, and still checks its sha256 and size, so edit the manifest whenever you edit the notice. `source_archives` (only heic2any's so far) lists release source archives hosted for a license: `path` in a `source/` folder next to the library, `source` URL, `sha256`, `bytes`, SPDX `license` and `of` (what it's the source of). heic2any's are libheif 1.10.0 and libde265 1.0.2 (the maintainers' GitHub release assets `libheif-1.10.0.tar.gz`, 1,681,115 bytes, and `libde265-1.0.2.tar.gz`, 806,562 bytes, byte-identical; the same sha256 is in Homebrew's libheif 1.10.0 formula and meta-openembedded's libde265 1.0.2 recipe), hosted so the LGPL source is on orisod.com too.
- **Files a page links to must open as text.** GitHub Pages sends a file with no extension (like `LICENSE` or `NOTICE`) as `application/octet-stream`, so a link to it downloads it instead of showing it. A license or notice file that a page links to gets a `.txt` name (heic2any's five text files were renamed so on 2026-10-29; their bytes are unchanged, and the manifest keeps their upstream `source`). Unlinked ones, like Tesseract's `NOTICE`, can stay as they are.
- **Files taken from a release tarball** (only Liberation Sans so far): when upstream publishes a file only inside a release archive, each vendored file keeps its upstream name, its `source` is the tarball's URL and `member` its path inside it, and the library has a `release_archive` with that `url`, the tarball's `sha256` and `bytes`, and `checksum_from` (where the published checksum it was verified against came from). CI checks the extracted files' own sha256 (it never downloads the tarball). To update: download the new tarball into an empty folder, verify it against a published checksum, extract, and copy the files unchanged.
- **Fetched at runtime (fonts):** a file a page loads with `fetch()` (Liberation Sans) sits in `assets/vendor` like a script, with the same manifest entry, and its path is written in the page script as a plain string (`FONT_FILES`), so `check_vendor.py` can check it. Fetch it only when it's needed, with a timeout and an error in the page's `role="alert"` error line (60 s), never falling back to a broken result. Tool pages keep their script inline, so the font code is one marked block ("Shared font loader: start" to "end": `BUILTIN_EXTRA`, `FONT_RANGES`, `FONT_FILES`, the timeout, `FontLoadError`, `inFont()`, `loadFontFiles()`, `useLiberationSans()`) copied byte for byte into PowerPoint to PDF and Excel to PDF (EN and ES); the smoke test fails if the four copies differ, so change it in one page and copy it to the other three. What each tool counts as drawable, its warning and its error wording stay outside the block.
- **Pages reference vendor files by root-absolute path** (`<script src="/assets/vendor/spark-md5/3.0.2/spark-md5.min.js"></script>`), the same string on the EN and ES page, in the same place as the CDN tag was (right before the tool's own script, never in `<head>`). Anything a library loads at runtime must be pointed at `assets/vendor` explicitly too (PDF.js's `workerSrc`; Tesseract's `workerPath`, `corePath` and `langPath`, as full URLs built from `location.origin`, because its worker starts from a `blob:` address where a relative path doesn't resolve).

Each library PR adds its case to `CASES` (vendor files, a list or a function of the language, page, and a `run()` that throws on a wrong result; `vendorOneOf` for files of which exactly one must load). The local server sends `.gz` files as `application/gzip` with no `Content-Encoding`, like GitHub Pages; tesseract.js unzips them itself.
- **Adding or updating a library** (never automatic):
  1. Download the exact file the pages use (pinned version, never a `latest` alias) and its license file into a new, empty temporary folder, not into the repo. Take the license from the library's repo at the matching tag when the package doesn't ship one.
  2. For an update, diff the new file against the current one and read the changes (new network calls, storage, anything built from the URL), and check GitHub's advisory database for the new version.
  3. Put it in a **new** `assets/vendor/<name>/<version>/` folder with its `LICENSE`, and add or update its manifest entry (source URL, `sha256`, `bytes`, SPDX license, `used_by`). `check_vendor.py` prints the real sha256 and size of any file that doesn't match.
  4. Point the pages at the new path (the same change on EN and ES), including anything the library loads at runtime (for Tesseract, the three paths with the new version folder).
  5. Run `python scripts/check_vendor.py` and `node scripts/test_vendor_smoke.js`, then `python scripts/verify_new_content.py --all`.
  6. Once no page uses the old version, delete its folder and its manifest entry in the same PR.
- **Offline:** self-hosting doesn't add offline support. There is no service worker, and GitHub Pages sends `Cache-Control: max-age=600`. An already open tool keeps working without a connection once its libraries have loaded (checked 2026-10-28 on the 4 tools above), but reloading or opening a page offline fails, as it did with the CDNs. Files a tool fetches on first use (PDF.js's worker, Tesseract's engine and language data) still need a connection the first time. No page claims offline use; the "Offline use" feature on the SaaSHub listing is the one flagged in the roadmap for removal.

## Browser checks in CI (`check-smoke`, added 2026-10-29)

`.github/workflows/check-smoke.yml` ("Verify pages and tools in a browser") is the 11th check (`check-filename`, added 2026-11-12, is the 12th; with `submit-sitemap.yml` that makes 13 workflows on `main`; `orisod-2` adds `check-styles` and `check-nav-sync`, 15 in all). It runs on every PR to `main` and every push to `main`, except when a change only touches `**/*.md`, `docs/`, `audit/` or `.claude/` (no check is required on `main`, so a skipped run can't block a PR). It has two jobs side by side (three on `orisod-2` since PR 6 of the download file names, where `smoke` was split in two, see below), each with a 10-minute timeout and the same setup as `check-a11y` (Node 22 with the npm cache, Chromium cached by the pinned Playwright version, system libraries installed only if Chromium can't start). A newer push to the same PR cancels the older run. Chromium only; there are no fixture files in the repo (every test file is written by the test).

The jobs load the pages in headless Chromium as `https://orisod.com/...`, answered from the checkout the way GitHub Pages answers them (a folder serves its `index.html`, an unknown path `404.html` with a 404). GoatCounter's counting request is answered locally, so nothing is counted, and every other host is blocked. Their shared helpers are in `scripts/browser_check_lib.js`.

- **`page-load`: `scripts/check_page_load.js`** loads every URL in `sitemap.xml` plus two broken URLs (`/ci-page-load-missing-page/` and its `/es/` twin, so the 404 page is loaded in both languages), 6 at a time. A page fails on any uncaught exception, console error, console warning, blocked or failed request, or 4xx/5xx response. The only allowed exceptions are the 404 page's own document status and the "Failed to load resource ... 404" line Chromium logs for it, on those two URLs. No retries: every file comes from the checkout. About 1 minute locally for all 314 pages.
- **`smoke`** first runs the **Node unit tests** in `scripts/tests/` (`node --test "scripts/tests/*.test.mjs"`, added 2026-11-04; no browser): each test cuts its block out of the page that ships it and runs that exact text, so the page and the test can't drift. The first is `blank_detection.test.mjs` for Remove Blank Pages' detection (see **Remove Blank Pages from PDF**). Then **`scripts/test_vendor_smoke.js`** runs every case (one real operation per tool library, EN and ES; see **Self-hosted libraries**). Console errors fail a case; console warnings are listed (WARN lines and the job summary) but don't, because of Chrome's `willReadFrequently` hint (Phase 14). Seen so far: the HEIC case's own pixel check in the test, and the PDF color filters case, whose page logs the hint itself (the Phase 14 item). About 75 seconds locally (78 page runs). **On `orisod-2` the smoke cases run as two parallel jobs (since PR 6 of the download file names, 2026-11-13, when the single job reached 5:48):** `smoke` runs the unit tests and `node scripts/test_vendor_smoke.js --group rest` (every case except the file name ones, 146 runs, about 4 minutes locally), and `smoke-file-names` runs `--group file-names` (the "Download file names (...)" cases, 134 runs, about 2 minutes locally). Without `--group`, the script still runs every case.
- **Failure messages:** every failure is printed as `FAIL <page>: <kind>: <message> (<file>:<line>)` and, in GitHub Actions, as an error annotation on that file and line: the line the browser named for an exception or console error, or for a failed request the page line that loads the file (the `<script src>`). Each job also writes a table to its job summary (page-load groups the failures by message). GitHub shows at most 10 error annotations per step, so the log and the summary have the full list.
- **Run them locally** from the repo root, after `npm install` and `npx playwright install chromium`: `node scripts/check_page_load.js` (it must end "All 314 pages loaded ... with no uncaught exception, console error or warning, blocked or failed request, or 4xx/5xx response.") and `node scripts/test_vendor_smoke.js` (it must end "All vendor smoke tests passed"). ## Download file names (`orisodFileName`, started 2026-11-12)

Every file a tool lets the user download gets a name that keeps the user's own file name and carries the site's identity: **[the input name without its extension]-[what the tool did]-orisod.[ext]**, for example `Contract-signed.pdf` merged becomes `Contract-signed-merged-orisod.pdf`. Owner decision (2026-11-12), rolled out in PRs; **the pilot (PR 1) covered Sign PDF, Compress PDF, Rotate PDF and Crop Image, PR 2 the other 22 single-file PDF tools, PR 3 the 20 image tools, PR 4 the 5 tools that make zips or several files and PR 5 the 13 generators, pasted-input and multi-input tools (EN and ES, 128 pages in all)**. That covered every tool with a download on `main` except Merge PDF and the WhatsApp link generator, whose scripts were rewritten on `orisod-2`: **PR 6 (on `orisod-2`, after `main` was merged into it by #224) gave them the helper, so the rollout is complete on both branches** (132 pages on `orisod-2`; on `main` the two pages keep their old names until `orisod-2` is merged). `PENDING_PAGES` in `check_filename.py` is now empty: every page that offers a download must carry the helper.

- **The rule** (all in `orisodFileName({ name, accept, action, ext, fallback, part, total })`):
  - `name` is the input file's name (for several inputs into one file, the first in the final order; `""` for none). `accept` lists the input extensions to strip, case-insensitive and repeated (`a.pdf.PDF` gives `a`); any other dot stays (`report.v2`).
  - A trailing `-orisod` is removed, and if the name then ends with this tool's own `-<action>` it isn't added again, so feeding a download back gives the same name, and different tools stack: `Contract-signed-orisod.pdf` rotated gives `Contract-signed-rotated-orisod.pdf`.
  - Cleaning: NFC; control characters, bidi controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) and `< > : " / \ | ? *` become `-`; runs of spaces become one space and runs of `-` one `-`; spaces, dots, `-` and `_` are trimmed at both ends. Accents, emoji, spaces and capitals stay as the user wrote them.
  - The base is cut to 120 UTF-8 bytes (`ORISOD_NAME_BYTES`) between whole characters (`Intl.Segmenter` graphemes, code points without it), so emoji sequences are never split and the action survives the cut. A Windows reserved name before a dot (`CON.backup`) gets a `-` for the dot; `CON` alone is fine because a suffix always follows.
  - Nothing left uses `fallback` (`document`/`documento`, `image`/`imagen`). `ext` is the real output format, lowercase, always last.
  - `action` is the tool's word in the page's language, ASCII, lowercase, hyphen-joined, written in the page's call: `signed`/`firmado`, `compressed`/`comprimido`, `rotated`/`girado`, `cropped`/`recortada` (PR 1); `numbered`/`numerado`, `stamped`/`sellado`, `cropped`/`recortado`, `pages-deleted`/`paginas-eliminadas`, `metadata`/`metadatos`, `filled`/`rellenado` (`filled-editable`/`rellenado-editable` when flattening fails and the fields are kept), `flattened`/`aplanado`, the N-up layout (`2up`, `4up`... in both languages), `booklet`/`folleto`, `filtered`/`filtrado`, `edited`/`editado`, `header-footer`/`encabezado-pie`, `organized`/`organizado`, `blanks-removed`/`sin-blancas` (Remove Blank Pages keeps it in its strings as `T.fileWord`, with `T.fileFallback`), `repaired`/`reparado`, `resized`/`redimensionado`, `watermarked`/`marca-de-agua`, `text`/`texto` (Extract PDF Text, `.txt`) (PR 2); `bordered`/`con-borde`, `blurred`/`difuminada`, `compressed`/`comprimida`, `filtered`/`filtrada`, `resized`/`redimensionada`, `rotated`/`girada`, `rounded`/`redondeada` or `circle`/`circulo`, `watermarked`/`marca-de-agua`, `no-exif`/`sin-exif`, and for Social Media Crop the preset's name folded to ASCII (NFD, marks removed, lowercase, hyphens: `instagram-post`, `publicacion-de-instagram`) (PR 3); Split PDF `extracted`/`extraido` for a range, a `split`/`dividido` zip of `page`/`pagina` entries; PDF to JPG a `pages`/`paginas` zip, `pages-selected`/`paginas-seleccionadas` for the selected pages, and `page`/`pagina` with the number on each JPG (a one-page PDF gives `<name>-orisod.jpg`, no word or number); Extract Images from PDF an `images`/`imagenes` zip of `image`/`imagen` PNGs (the same names saved one by one); OCR PDF `ocr` in both languages for the `.pdf` and the `.txt`; Favicon Generator, which has no input name to keep, `favicon-package-orisod.zip`/`paquete-favicon-orisod.zip` (its fallback word) (PR 4); the generators have no input, so their word is the fallback and no action is passed: Calendar generator `calendar-<year>`/`calendario-<year>` (the selected year), Hebrew calendar generator `hebrew-calendar-<year>`/`calendario-hebreo-<year>` (the selected Hebrew year, also in Gregorian-year mode), Handwriting Worksheets `handwriting-worksheet`/`ficha-de-caligrafia`, Text to PDF `text`/`texto`, QR Code Generator `qr-code`/`codigo-qr`, Convert to Markdown `markdown` (`.md`, both languages), Collage Maker `collage` (`.png` or `.jpg` as chosen, whatever the photos are called) and Image to Base64's decode `decoded-image`/`imagen-decodificada`, whose extension comes from the decoded bytes (`decodedImageExt()`: PNG, JPEG, GIF, WebP, BMP, AVIF, ICO or SVG by their first bytes, otherwise the data URL's own type when it's a plain word, otherwise `png`), so a JPEG pasted without a prefix or labelled `image/png` saves as `.jpg`; removing it makes the next one first), Alternate & Mix Pages File A with `mixed`/`intercalado`, Compare PDFs File A with `compared`/`comparado` (`.txt`) (PR 5); Merge PDF the first PDF in the list as merged (after reordering or removing) with `merged`/`unido`, and the WhatsApp link generator's QR code `whatsapp-qr-orisod.png` in both languages, a fixed word (PR 6, `orisod-2`). ## Theming (light/dark)

- Two themes only: dark (default) and light. A sun/moon toggle button lives in the nav's icon row (on `orisod-2` two Lucide icons, the one shown picked by CSS: see **Lucide icons** under Orisod 2.0); it sets `data-theme="light"` (or removes it for dark) on `<html>` and persists the choice in `localStorage` (key `orisod-theme`). The only other key is `orisod-wa-country` (the WhatsApp link generator's last country, never the number or the message); `/privacy/` and `/es/privacy/` name both, so update them if a key is ever added. A tiny inline script at the very top of `<head>` reads that value and applies it before first paint, to avoid a flash of the wrong theme.
- Colors are expressed as CSS custom properties defined in `:root` (dark values) and overridden under `:root[data-theme="light"]` — never hardcode a raw hex for something that should flip between themes. Core variables: `--bg`, `--text`, `--card-bg`, `--border`, `--accent`, `--muted-text`, `--dropzone-border`.
- When adding new UI to any page, use the existing variables rather than introducing new hardcoded colors, so it stays correct in both themes automatically.
- **Both themes are checked for contrast (added 2026-10-07).** `scripts/check_a11y.js` (CI: `check-a11y`) scans every page twice, in dark and then in light theme (it flips `data-theme="light"` with transitions off), and reports which theme each violation is in. Until then CI only checked dark theme, so 24 light-only contrast failures had built up unnoticed. The fixes set the pattern for light-theme text colors: light-blue text (`#60a5fa`, used for inline links and `<code>`) becomes `#1d4ed8` in light theme. Amber text (`#f59e0b`) becomes `#92400e`, the same pair the `.disclaimer` box uses. Plain `--accent` (`#2563eb`) is too faint for small text on white inside the 0.85–0.9 opacity paragraphs these pages use. Watch for an `opacity:1` that a more specific `.box p{opacity:.85}`-style rule silently overrides.
- **Every page has a subtle CSS grid/atmosphere background, driven by a `--grid-alpha` token** (added to home/`/tools` first, extended to all 44 tool pages in PR #3/commit `59d90d5`, and to all 42 blog posts EN+ES on 2026-08-24 — now live everywhere). Values: `--grid-alpha:.05;` in `:root{}` (dark), `--grid-alpha:.10;` in `:root[data-theme="light"]{}` (light needs more contrast to read against a near-white background — .035 was tried first and was effectively invisible). Applied via `body{background-color:var(--bg);background-image:linear-gradient(rgba(148,163,184,var(--grid-alpha)) 1px, transparent 1px),linear-gradient(90deg, rgba(148,163,184,var(--grid-alpha)) 1px, transparent 1px);background-size:42px 42px;...}` (replaces the plain `background:var(--bg);` shorthand — note the transition property also changes from `background 0.2s` to `background-color 0.2s`). Every new page must include this exact block — see the Working conventions checklist below.
- **`.theme-toggle` CSS must be self-contained, including an explicit `margin:0`.** Every tool page defines its own generic `button, .back{...}` rule for that tool's action button (e.g. "Compress Image"), and that bare `button` element selector applies to *every* `<button>` on the page — including the nav's `<button class="theme-toggle">`. Class selectors on `.theme-toggle` (like `display`, `padding`, `background`) already win over the element selector on specificity, but `margin` is a property the tool's generic `button` rule sets and `.theme-toggle` didn't use to set, so it fell through unopposed and visibly misaligned the toggle relative to the EN/ES pills next to it. The standard `.theme-toggle` rule now is: `box-sizing:border-box;display:inline-flex;align-items:center;justify-content:center;height:30px;margin:0;padding:0 9px;background:var(--card-bg);border:1px solid var(--border);border-radius:6px;color:var(--text);cursor:pointer;font-size:15px;line-height:1;` — and `.lang-flag` uses the matching box model (`box-sizing:border-box;display:inline-flex;align-items:center;justify-content:center;height:30px;padding:0 10px;...`) so both sit on an identical height/baseline regardless of being an `<a>`/`<span>` vs a `<button>`. When propagating the nav to a tool page, always use these exact rules rather than copying the tool page's pre-existing `.lang-flag`/theme styles verbatim.

## Custom 404 page (added 2026-10-06, expanded 2026-10-06, Spanish wired up 2026-10-07)

`/404.html` (repo root, a file, not a folder) is the site's custom error page. GitHub Pages serves it for every unmatched path on orisod.com with a real HTTP 404 status (verified live). It is **one file for both languages**: GitHub Pages has no per-folder 404 support, so there is no `/es/404.html`. The HTML is English, which is what no-JS visitors always get. When the broken URL starts with `/es/`, the page's script (`localizeToSpanish()`) translates it in place from the `COPY.es` JS object: `<html lang>`, title, heading, both message pools, all three link labels, gear hints and button labels, the nav and footer text (copied from the live `/es/` pages; keep `COPY.es.chrome`/`COPY.es.nav`/`footerHeadings`/`footerBrandDesc`/`footerSupportText` in sync if the Spanish nav or footer ever changes; `COPY.es.nav` holds the minimal nav's button, search-box and menu labels, and only the text of each menu item is swapped so its icon stays), and the EN/ES switch in the menu's Language row (ES active, EN links to `/`), and the nav search box submits to `/es/tools/`. It also points every site link at its `/es/` version (prefixing `/es`), and "Let the gears choose" draws from `/es/tools/` instead of `/tools/`. A future language would follow the same pattern: add `COPY.<lang>`, detect its prefix, and generalize `localizeToSpanish()`. Because it's served at arbitrary depths (`/es/a/b/c`), every URL in it must be root-absolute. It has `<meta name="robots" content="noindex">`, no canonical/hreflang, and is deliberately **not** in `sitemap.xml` (`check_sitemap.py` only looks at `index.html` files, so it never asks for one). `check_nav.py` explicitly adds it to its page list, and `check_a11y.js` scans it once per gear variant, on both an English and a broken `/es/` URL, via `EXTRA_PATHS` (its local server serves `404.html` for unmatched paths, like GitHub Pages), since neither would pick it up otherwise.

**Rule: the page resolves first, plays second.** With zero interaction and with JS disabled, it shows the fixed `<h1>` "404: This page slipped out of gear." (colon, not an em dash, per editorial rule #1; never rotates), a message, and three plain `<a href>` links: "Browse all tools" (`/tools/`), "Let the gears choose" (fallback href `/compress-image/`; JS upgrades it to a random tool by fetching `/tools/`, or `/es/tools/` on a Spanish URL, and reading its `a.tool-card` links, so there's no separate tool list to maintain), and a smaller text link "Return home" (`/`). Nothing below may ever gate, delay or hide those.

**Rotating messages:** two pools of 6 in `COPY.en` (and `COPY.es` for `/es/` URLs): `preFix` (one picked at random on load) and `postFix` (one picked at random when the gear is fixed). They are picked independently of each other and of the gear variant. The HTML default is pre-fix #3 ("This page took a wrong turn, and the gears followed."), because it doesn't ask for a repair and so reads right with JS off, when no gear shows. Under `prefers-reduced-motion` the pre-fix pick is limited to #3 and #6 for the same reason: the gears appear already fixed and can't be clicked. `aria-live` is added to the message only after the initial pick, so only the post-fix swap is announced.

**Gear easter egg:** an optional, discreetly hinted `<button>` under the links, reusing `/assets/gear-base.png` and the homepage hero's 10:7 CW/CCW spin pairing. Each load picks 1 of 6 variants at equal odds (force one with `?gear=loose|stuck|tooth|sync|rusty|offcenter` on any broken URL): **loose** (small gear sits apart and bobs; click/tap/Enter or a drag snaps it into mesh), **stuck** (gear twitches but won't turn; each click nudges it, the 3rd frees it), **tooth** (top tooth masked off with CSS `mask`, gear hiccups round; 1st click floats the tooth back halfway, 2nd seats it), **sync** (both gears turn the same way and the small one shudders; one click reverses it), **rusty** (gear dulled with a CSS `filter` on the same blue image, creaking; 3 clicks polish it back via `--rust`), **offcenter** (gear orbits around an off-center pivot; 3 clicks or drags pull `--off` to 0 and center it). Every variant fixes the same way: each gear's current angle is frozen on its `.ph` wrapper, then it eases up to speed (`gUp*`, 1.2s ease-in) and hands off to a steady loop (`gLoop*`), so there's no snap; one soft accent-colored radial glow pulses behind the stage (`.stage::before`). The only other effect is the post-fix message. No scores, timers, new controls or reveals, ever, and no colors outside the existing accent. The egg is `hidden` until its script runs (no-JS visitors never see a dead control). Under `prefers-reduced-motion` it renders the already-fixed gears as a static, disabled, `aria-hidden` picture with no glow. To add a 7th variant: add an entry to `VARIANTS` (clicks, html built from `gear()`/`PAIR`/`SOLO` so gears carry `data-dir` and a `.ph` wrapper), any per-step effect to `advance()`, its `.v-<name>` CSS (broken state + `.fixed` state; leave the fixed spin to the shared `.stage.fixed [data-dir]` rules), add its `label`/`hint` to `gears` in both `COPY.en` and `COPY.es`, add the name to `names`, and add it to `GEAR_VARIANTS` in `scripts/check_a11y.js`.

Posts show no visible date. - Text in JSON-LD follows the editorial rules (no em dashes) and reuses existing page text verbatim; never reword a title or meta description to fit.
- `scripts/check_jsonld.py` (CI: `check-jsonld`) fails on invalid JSON, a missing or duplicated type, any url/item that isn't the canonical, a missing required field, a publisher/author that isn't the stub, any rating or review, a headline or WebApplication name that isn't the H1, FAQ text that isn't the visible text, a wrong `applicationCategory`, a future or out-of-order date, an em dash, or a `BreadcrumbList` with no visible breadcrumb. It takes `--root DIR` so it can be run against a test copy. It can't check that `dateModified` is up to date (CI has no full git history), so run `content_dates.py`.

## Editorial & accessibility standards for new pages

These 4 rules apply to every new tool page, blog post, and guide from day
one — the goal is to never need another retroactive cleanup pass on these
categories again. The first documents a convention that's been enforced
across 4 cleanup rounds (Phase 12b PRs #81-87; PRs #88-92; PRs #93-100; and
a third-audit round covering accessibility/JSON-LD/headings) but was never
actually written down until now; the other 3 are new standing rules.

1. **No em dashes in visible content.** Use a comma, colon, parentheses, or
   a period splitting into two sentences instead — never an em dash (—) in
   anything a visitor reads or a screen reader announces. Two standing
   exceptions, permanent, not subject to a future cleanup pass: `<title>`
   and `<meta name="description">` tags are never rewritten for tone at all
   (risk of stripping "Free"/"Online"/"Gratis" from SEO-critical text — a
   Phase 12b decision). JS string literals inside `<script>` blocks
   (dropzone/progress/error messages) used to be an accepted gap too, but
   visitors do see them: the 88 em dashes there were rewritten on 2026-10-22,
   along with "file(s)"/"page(s)" plurals (pick the word from the count
   instead, e.g. `${n === 1 ? 'file' : 'files'}`). `scripts/check_copy.py`
   (CI: `check-copy`) now fails any script string with an em dash or a
   "(s)" plural; AI Writing Checker's em-dash detector is its one allowed
   exception. Never write a bidi control character (the Arabic letter mark,
   LRM, RLM, U+202A to U+202E, U+2066 to U+2069) literally in code: they're
   invisible and can make code read differently from what it does. Use an
   escape (`\u200F`). `scripts/check_bidi_chars.py` (CI: `check-copy`, with
   `scripts/test_check_bidi_chars.py` proving it fails) checks `scripts/`, the
   site's own JS and JSON and every page's inline scripts; page text outside
   scripts is content, where an RLM in Hebrew is fine.
2. **Every form control ships with a programmatic label.** Connect every
   `<input>`, `<select>`, `<textarea>`, and slider to a real `<label for=
   "id">` — reuse the control's existing visible label text as the `for`
   target rather than duplicating it in an `aria-label`. Only use
   `aria-label`/`aria-labelledby` when there's genuinely no visible label
   to reference (e.g. an icon-only control). Never rely on placeholder text
   alone — placeholders aren't reliably announced by assistive tech and
   disappear the moment the user types.
3. **Every new tool/post ships with JSON-LD from day one**, matching its
   page type: tool pages get `WebApplication` + `FAQPage` (built from that
   page's own real `.faq-item` Q&A content) + `BreadcrumbList`; blog/guide
   posts get `BlogPosting` + `BreadcrumbList` (no `FAQPage` — posts don't
   have genuinely structured FAQ markup, and forcing it risks a
   wasted/ineligible rich result). The tool/post `BreadcrumbList` (added
   2026-10-20, Initiative 2) is a separate `<script type="application/ld+json">`
   right before `</head>` and must list exactly the visible breadcrumb trail
   (see **Breadcrumbs**); `check_breadcrumbs.py` enforces that. Index
   pages (blog index, `/tools`) get no JSON-LD at all since 2026-10-23
   (their old `BreadcrumbList` was removed because they show no visible
   breadcrumb), and never an `ItemList`/`CollectionPage` enumerating every
   post/tool (the site already has 3+ hand-synced duplicates of that list,
   homepage search array, related-cards and `/tools/index.html` itself; a
   4th adds staleness risk for marginal value). Schema must strictly
   reflect only what's on the page: never invent a rating, review count
   or author name, and post dates come only from the post's real git
   history. The full design, including the Organization `@id` stub and
   the post date rules, is in **Structured data (JSON-LD)**;
   `check_jsonld.py` enforces it.
4. **Sequential heading levels only — H1 → H2 → H3, never skip a level.**
   If a tool's settings panel uses H3 sub-labels for control groups, it
   needs a parent H2 container (reuse an existing visible section label as
   the H2 text where one already exists, rather than inventing new copy).
   Watch for CSS: if headings are styled by a bare tag-selector (`h2{...}`)
   rather than a class, adding or changing a heading level without a
   matching scoped class can visually break — a settings-panel H3 promoted
   to H2 without its own class will inherit the larger content-section H2
   style instead of staying compact.

## Shipping a new tool or post: pre-merge content audit (added 2026-10-25)

Every new tool or post (the 4 pages, EN+ES) is audited before its PR is merged, with the same process as Phase 12b and the Hebrew calendar guides (PRs #81-87, #136), now kept as scripts. On the feature branch, once the pages are written:

1. **Extract:** `python scripts/audit_extract.py` writes every block of text on the pages added or changed vs `main` to `audit/out/review.json` (gitignored), including `<li>`, FAQ answers, card blurbs, figcaptions, alt text and SVG labels. Pass file paths to pick pages yourself. Check its "uncovered text" warnings: they mean a block was missed.
2. **Audit with ChatGPT:** paste `audit/chatgpt-instructions.md` (below its line) and attach the JSON. Save the file it returns as `audit/out/review.reviewed.json`. Don't retype the instructions; change the rules in that file.
3. **Apply and verify:** `python scripts/audit_apply.py audit/out/review.reviewed.json` (dry run), then the same with `--write`. It writes only blocks whose hash still matches the page and that are editable, and it keeps og: tags and JSON-LD in step. If anything is mismatched or rejected it writes nothing. Then run `python scripts/sync_related_cards.py --write` (Related tools cards come from `/tools`, never from the audit), `python scripts/content_dates.py --write` and `python scripts/verify_new_content.py`, which must say "All checks passed".
4. **Report and wait:** report the apply counts (changed / unchanged / excluded / rejected / mismatched) and the verify result in the PR, then wait for the owner's explicit approval before merging.

Rules the scripts enforce:
- **Sentence case** for `<title>`, meta descriptions, H1s and card text: first word and the first word after a colon or pipe capitalized, proper nouns and acronyms (Orisod, PDF, JPG, PNG, HEIC, URL, JSON, UUID, iPhone, Base64...) as written, everything else lowercase. Tool names ("Compress Image") keep their capitals.
- **`<title>` and `<meta name="description">` wording never changes** in an audit: only capitalization and punctuation may (`audit_apply.py` refuses anything else).
- **JSON-LD** must match the page (see **Structured data (JSON-LD)**); `verify_new_content.py` runs `check_jsonld.py` with the other CI checks.
- **Sitemap and post dates come from `python scripts/content_dates.py --write`**, never typed by hand; `verify_new_content.py` fails while a date is out of date.
- **"Read our guide" / "Lee nuestra guía" link text equals the guide's H1** (since 2026-10-27): change the post's H1, then run `python scripts/sync_guide_links.py --write` (`--check` exits 1 on any mismatch); `verify_new_content.py`'s guide-sync check fails otherwise.

`verify_new_content.py` stays a manual, local runner and is deliberately not in CI (decision confirmed 2026-09-07). `--all` runs its page checks on every page; `--a11y` adds the axe scan.
